# The SLM Brain: Research Design

> Research track for running Thirties fully on-device with a small model (Gemma 4-E4B / E2B via LiteRT-LM). `AGENTS.md` §4 explains how this brain sits next to the Frontier Brain on the shared core. Sequencing is in `docs/ROADMAP.md` (Phase 5).
>
> Everything below the "Premise" is a **starting hypothesis to be tested by evals**, not settled design.

---

## 1. Premise

Gemma 4-E4B is *extremely* weak at this task. It cannot reliably hold a schedule in its head, count blocks, rank thirty notes, or follow a long rule list. A trimmed-down frontier prompt fails. The SLM brain therefore has to be built differently from the start: the model contributes as little as possible, in the smallest possible pieces, and deterministic Python does everything else.

---

## 2. Design Principles

1. **One tiny decision per model call.** Never ask the model to understand the message, pick the action, fill arguments and write a reply all at once.
2. **Constrained output.** The model fills a small fixed schema (an intent label, or a handful of slots). Use grammar- or schema-constrained decoding if LiteRT-LM supports it. Otherwise validate strictly and retry or ask the user.
3. **Python does selection, math and checking.** Python parses times ("4:30", "after lunch" when defined), resolves which event "it" refers to when possible, finds open time, detects conflicts, and pre-scores backlog candidates.
4. **Small, fresh context.** Each call gets a short, purpose-built context written by Python: the relevant few events and a handful of candidates. Never a long transcript.
5. **Same tools as the Frontier Brain.** The SLM brain calls `PlanTools` and nothing else. Any tool it needs that the Frontier Brain does not belongs in the shared core.
6. **Templated replies where possible.** Confirmations and conflict reports can be generated by Python from tool results. Use the model for free-form wording only where it adds real value.

## 3. Sketch Pipeline (hypothesis)

```
user message
   │
   ├─▶ [model] intent router ──▶ one of: add / move / remove event, log outcome,
   │                              ask about schedule, ask for a suggestion,
   │                              confirm / reject pending proposal, chit-chat
   │
   ├─▶ [model] slot filler for that intent (tiny schema, constrained output)
   │
   ├─▶ [python] resolve slots (times, event references, candidates) and validate
   │          ├─ ambiguous or invalid ──▶ templated clarifying question
   │          └─ ok ──▶ PlanTools call
   │
   └─▶ [python, optionally model] reply from the tool result
```

Suggestions ("what should I do this afternoon?") follow the same pattern. Python pre-scores the backlog and finds open time; the model only picks or phrases among a few prepared options.

### Backlog pre-scoring (carried over from the earlier SLM plan)

A deterministic score ranks the whole backlog before the model sees anything, for example:

`Score = DeadlineWeight(due_date) + CategoryWeight + DeferralPenalty − Friction`

The model sees the top 3–5 candidates with short reasons ("due in 5 days", "deferred 3x"). Category weights must not encode fixed daylight/dark rules (AGENTS.md §2.3). Physical constraints and the user's own learned preferences (Phase 4) are fine.

## 4. Evaluation: The Development Engine

For this brain, the harness *is* the development process. We do not tweak prompts by feel.

### 4.1. What exists
- `tests/run_eval_harness.py`: combinatorial scenario generation (personas, messy communication styles, task loads, calendar conflicts) and a persistent GPU daemon with crash isolation. This provides **breadth**.
- `tests/interactive_eval.py`: turn-by-turn stepping with real state deltas, checks of claims against reality, and scorecards. **The judge is an agent (or a human) stepping through the session.** This provides **depth**.
- `tests/run_qualitative_battery.py`: 25 curated scenarios. Its built-in scoring is keyword matching that starts every turn at 5/5. Its "25/25, 98%" result does not measure quality and should not be cited.

### 4.2. Plan
1. **Reconcile the harnesses.** Feed scenarios from the combinatorial generator (`--seed`, `--count`) or the curated set into the stepping engine, so batch and interactive runs share the same delta tracking and scoring.
2. **Frontier reference.** Run every scenario through the Frontier Brain as well. Compare the final schedule state (span by span, after Phase 1). Agreement is a cheap automatic signal. Disagreements go to the agent judge, which also decides when the Frontier answer is the wrong one.
3. **Per-stage evals.** Because the pipeline has separate stages, test each one alone on labelled utterances: router accuracy, slot accuracy, time-resolution accuracy. The Frontier model can produce labels at scale, and the agent judge spot-checks them. This is the main payoff of the pipeline design: failures point at a specific stage.
4. **Tiers.**
   - Tier 1: about 10 fast regression scenarios with mock engines, run on every commit.
   - Tier 2: the curated qualitative set against real Gemma.
   - Tier 3: 100–500 generated multi-turn scenarios for robustness, memory and invariants.
5. **Root-cause categories for failures:**
   - arithmetic or time-resolution mistakes, which means move the work into Python;
   - context saturation, which means tighter pre-scoring or a smaller context;
   - router or slot confusion, which means change the schema, add examples, or split the stage;
   - invariant violations, which means add a deterministic guard in `PlanTools`.
6. **Output hygiene.** Raw sessions and transcripts go to `docs/eval_reports/` (gitignored). Commit only curated summaries.
